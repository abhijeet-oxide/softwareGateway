# software-gateway

The Coordinator, the worker fleet, the web tier, the policy decision point and
the identity provider. Optionally the PostgreSQL cluster they use.

Everything a deployment differs in goes in one values file. Annotated examples:
[`deploy/examples/`](../../examples).

## Two layers, one values file

The chart renders two layers, selected by `layers`:

| layer | renders | why it is separate |
|---|---|---|
| `database` | a CloudNativePG `Cluster` | a `helm rollback` of the application must not be able to reach the database, and `helm uninstall` must not delete it |
| `application` | everything else | the ZITADEL migration is a Helm pre-install hook, which needs the database to already exist |

Under Flux they are two `HelmRelease` objects reading the **same** values
ConfigMap, the database one first — see [`deploy/flux`](../../flux).

For a self-contained `helm install`, turn both on and install twice: once with
`--set layers.application=false`, then again with the defaults.

## What a deployment states

```yaml
access:
  webUrl:      https://gateway.example.internal
  identityUrl: https://id.example.internal
  expose:
    type: ingress
    ingress: {className: nginx}

images:
  registry: registry.example.internal
  mirror: registry.example.internal/docker
  pullSecrets: [registry-pull]
```

Everything else has a default that works. ZITADEL's master key and root password
are generated on first install and read back on every upgrade; the database
password is generated by CloudNativePG.

## Addresses

`access` is the single source for every browser-facing URL. The identity URL is
stamped into every token's `iss` and is the Host header ZITADEL matches against,
so it is derived rather than restated — an ingress host and an issuer cannot
disagree.

`access.expose.type` chooses how those addresses are published:

| type | renders | use it when |
|---|---|---|
| `none` | nothing | your own reverse proxy is pointed at the `web` and `zitadel-proxy` Services |
| `ingress` | one Ingress per address | the cluster runs an ingress controller and the hosts resolve |
| `route` | one Route per address | OpenShift |
| `loadBalancer` | one Service per address | a lab with no DNS — set the hosts to the load balancer IPs |
| `nodePort` | one Service per address | a lab with no DNS and no load balancer; the browser's port IS the node port |

`ingress` and `route` route on the Host header, so the chart refuses an IP
literal there and names the alternative.

## Credentials

`config/secrets/secrets.yaml` is the inventory: names, keys and a relative path,
no values. `secrets.backend` picks the operator that turns each entry into a
Kubernetes Secret — `vault`, `azureKeyVault`, or `none` for Secrets made some
other way. The Secret that lands is identical either way.

`secrets.registryPullSecret` produces the kubelet's pull Secret from the same
inventory and adds its name to `images.pullSecrets`, so the credential the
pipeline pushes with is the one the cluster pulls with, held in one place.

## What a change costs

| change | cost |
|---|---|
| a product, a Cerbos policy | nothing restarts — all three watch their directories |
| a person, a role grant | one Job runs; no pod is touched |
| `config.yaml`, an image | a rolling update with `maxUnavailable: 0` |

A bad image therefore never takes capacity away: the rollout stalls with the old
pods serving, and Flux's remediation rolls it back.

## Validation

`values.schema.json` is checked by Helm before the render. `templates/_validate.tpl`
then fails on the mistakes that produce a stack which comes up green and does not
work — a half-mirrored registry, an issuer that no entry point serves, a pull
secret nothing creates, a product naming a credential nobody declared.
